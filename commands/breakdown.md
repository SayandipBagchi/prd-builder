Use the `planning-task-breakdown` skill.

Check the definition-of-ready gate before proposing anything. On a not-ready verdict, or no review at all, stop and name what fails. Proceed only on an explicit override, and when overridden, stamp the override block into the preview and into every ticket description.

Resolve the tenant profile, then the parent issue. Establish the ownership boundaries, client through dependent modules, and confirm the grouping before producing the ticket preview.

Show every proposed ticket in full before any write. Wait for an instruction to create them; agreement that the breakdown looks right is not an instruction.

Discover the current create metadata for the target project and issue type before writing. Never hardcode a field ID or an option value from an example issue, and ask rather than fill a required field the source does not answer.
